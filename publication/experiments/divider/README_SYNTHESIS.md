# Эксперимент: Синтез схемы делителя напряжения

Этот эксперимент оценивает способность LLM-моделей синтезировать корректные схемы делителей напряжения по заданным техническим требованиям.

## 📁 Структура файлов

### Основные файлы:
- `voltage_divider_synthesis_experiment.py` - **Основной скрипт эксперимента**
  - Класс `DividerSynthesisAgent` для работы с LLM моделями
  - Функция `create_synthesis_test_cases()` - создание тестовых случаев
  - Функция `validate_synthesized_circuit()` - валидация синтезированных схем
  - Функция `run_synthesis_experiment_for_model()` - запуск для одной модели
  - Функция `analyze_synthesis_performance()` - анализ результатов

- `run_synthesis_single_model.py` - **Запуск для одной модели**
  - Удобный скрипт для тестирования отдельной модели
  - Показывает метрики после завершения

- `models_config_extended.json` - **Конфигурация 12 моделей**
  - GPT-4o, GPT-4o-mini, GPT-4 Turbo
  - Claude 3.5 Sonnet, Claude 3 Opus
  - Llama 3.1 70B, Llama 3.1 8B
  - Mistral Large, Mistral 7B
  - Qwen 2.5 72B, Qwen 2.5 7B
  - DeepSeek Chat

## 🎯 Цель эксперимента

Оценить способность LLM-моделей:
1. **Синтезировать схемы** по техническим требованиям
2. **Генерировать корректные netlist** в формате SPICE
3. **Выполнять правильные расчеты** (Vout, ток, мощность)
4. **Учитывать все требования** (ток, мощность, импеданс, защита)
5. **Избегать типичных ошибок** (8 типов ошибок)

## 📊 Тестовые случаи

Создано **15 тестовых случаев** для синтеза:

1. **Базовый делитель 3.3В** - простое ТЗ
2. **Батарейное питание** - низкий ток потребления
3. **Делитель с учетом нагрузки** - требование к выходному импедансу
4. **Делитель для АЦП** - работа с аналого-цифровым преобразователем
5. **Делитель с защитой** - обязательная защита от перенапряжения
6. **Прецизионный делитель** - требования к TCR
7. **Промышленный делитель** - ограничение мощности
8. **Делитель для IoT** - ультранизкое потребление
9. **Делитель с высоким током** - нагрузочная способность
10. **Граничный случай** - минимальный ток
11. **Делитель с RC-фильтром** - фильтрация помех
12. **Делитель для высокого напряжения** - 48В с защитой
13. **Делитель с точным соотношением** - требование к соотношению R1:R2
14. **Делитель для низкого напряжения** - 1.8В
15. **Делитель с множественными требованиями** - сложный случай

## 🔍 Валидация синтезированных схем

### 1. Проверка формата netlist
- Парсинг SPICE netlist из ответа LLM
- Проверка синтаксиса (V1, R1, R2, узлы)
- Извлечение значений R1, R2, Vin

### 2. Проверка расчетов
- Расчет Vout = Vin * R2 / (R1 + R2)
- Расчет тока I = Vin / (R1 + R2)
- Расчет мощности на каждом резисторе
- Расчет выходного импеданса R_out = R1 || R2
- Сравнение с расчетами LLM

### 3. Проверка соответствия требованиям
- Выходное напряжение в пределах допуска
- Ток не превышает максимальный
- Мощность не превышает допустимую
- Выходной импеданс соответствует требованиям
- Ток достаточен для АЦП (если указано)
- Наличие защитных элементов (если требуется)

### 4. Проверка на ошибки
Используются те же 8 типов ошибок:
- **Type 1**: Неверное соотношение резисторов
- **Type 2**: Слишком маленькие номиналы
- **Type 3**: Слишком большие номиналы
- **Type 4**: Игнорирование нагрузки
- **Type 5**: Проблемы с АЦП
- **Type 6**: Превышение мощности
- **Type 7**: Отсутствие защиты
- **Type 8**: Игнорирование TCR

## 📈 Метрики оценки

### Метрики синтеза
- **Success Rate**: доля успешно синтезированных схем (валидный netlist)
- **Calculation Accuracy**: точность расчетов (Vout, ток, мощность)
- **Requirements Compliance**: соответствие требованиям
- **Error Rate**: доля схем с ошибками

### Метрики по типам ошибок
- Количество ошибок каждого типа
- Частота ошибок каждого типа

## 🔧 Требования

- Python 3.9+
- Зависимости из `requirements.txt`
- API ключи для моделей (OpenRouter или OpenAI)
- Переменные окружения:
  - `OPENROUTER_API_KEY` (для большинства моделей)
  - `OPENAI_API_KEY` (для GPT моделей через OpenAI)

## 💡 Особенности реализации

1. **Парсинг netlist**: Используются регулярные выражения для извлечения компонентов из SPICE netlist
2. **Валидация расчетов**: Сравнение расчетов LLM с эталонными расчетами
3. **Проверка требований**: Автоматическое извлечение требований из текста ТЗ
4. **Обнаружение ошибок**: Использование тех же критериев, что и в эксперименте анализа
5. **Structured Output**: Поддержка JSON schema для моделей, которые это поддерживают

## 📝 Примечания

- Эксперимент может занять значительное время (10-15 минут на модель)
- Стоимость API вызовов зависит от модели и количества тестов
- Результаты сохраняются после каждого теста для возможности восстановления
